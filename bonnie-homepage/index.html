My Projects

  • Cyberattack Detection with Machine Learning

    Machine Learning

    I trained an image-recognition AI to detect cyberattacks in network traffic.

    Python Transfer learning Fine-tuning a CNN (ResNet-18) Handling imbalanced data (class weights, SMOTE) Data preprocessing Model evaluation (macro F1) Jupyter / Colab
    View on GitHub Colab notebook

    Purpose

    Traditional security systems use fixed rules, which struggle with new kinds of attacks. I wanted to test whether a model pretrained on everyday photos (ResNet-18) could be reused to learn attack patterns directly from data. This was a course project for DS340 Machine Learning, done with a teammate.

    What I did

    I used the NSL-KDD dataset, where each network connection has 41 measurements and belongs to one of five classes: Normal, DoS, Probe, R2L, and U2R. I turned each connection's measurements into a small 32x32 image so the model could "look" at it, then fine-tuned ResNet-18 in two stages. Some attack types are extremely rare (U2R is only 0.04% of the data), so I compared several fixes: class weights, SMOTE (creating synthetic examples of rare classes), and merging the two rarest classes into one "Others" class. My best model scored 0.74 macro F1 (an accuracy score that counts rare classes equally), about 25% better than the 0.59 Random Forest baseline.

    What I learned

    No single fix for imbalanced data solved everything, because each one had a trade-off. For example, class weights helped one rare class but hurt another. Changing how the classes were defined (merging the two rarest) helped more than any reweighting trick, so how you frame the problem can matter as much as the model. Detecting rare attacks is still an open problem: even my best model only found 19% of the "Others" attacks.

  • File Carver

    Digital Forensics

    A C program that recovers deleted or hidden files from a raw disk image.

    C programming Digital forensics (file carving) Binary file formats and signatures Probability and false-alarm analysis Shell scripting Python SHA-256 verification Technical writing
    View on GitHub

    Purpose

    When a file is deleted, its data can still sit on the disk even though the file system no longer points to it. I built this as a digital forensics (DFIR) learning project to understand how investigators recover that data.

    What I did

    I wrote a small tool in C that scans a disk image byte by byte, looks for the special start and end bytes ("signatures") of PNG, JPEG, and PDF files, and recovers them. The disk image is opened read-only, so the evidence is never modified. I tested it on disk images I built myself, so I always knew the correct answer, and checked each recovered file with a SHA-256 hash. I also measured false alarms by running it on 200 random disks with nothing hidden.

    What I learned

    A short start signature produces false alarms: a 3-byte JPEG signature gave 46 false hits on 200 random disks, close to the 50 that probability predicted. A false start can even swallow a real file, so a total file count that looks right can hide a lost file. Using longer, more specific signatures cut false alarms from 46 to 1, but the tool now misses some JPEG variants, which taught me that there is always a trade-off between avoiding false alarms and catching everything. I also learned to be honest about limits: it has only been tested on synthetic disks, and it cannot recover fragmented files.

  • SSH Honeypot Threat Intelligence Report

    Threat Intelligence

    I am analyzing real attack data from a decoy SSH server to understand how attackers behave.

    Python pandas Jupyter Data cleaning and pipeline design Honeypot log analysis (Cowrie) Threat intelligence Privacy-aware data handling Data validation
    View on GitHub

    Purpose

    A honeypot is a decoy server that attracts attackers so you can study what they do. Instead of running a risky live honeypot, I chose to analyze a large real dataset so I could put all my effort into data work: parsing, cleaning, statistics, and clearly communicating results as a cyber threat intelligence (CTI) report.

    What I did

    I am using the public CyberLab honeynet dataset, collected by a honeypot called Cowrie. My sample covers three days (186,015 attack sessions and 993,448 events). I built a two-stage pipeline: stage one cleans the raw data day by day, and stage two aggregates it and removes sensitive details such as plaintext passwords and attacker IP identifiers before anything is published. The pipeline ends with an integrity check that fails loudly if the row counts don't match. Next I plan to analyze password-guessing patterns, groups of attackers using the same tools, and what attackers do after logging in.

    What I learned so far

    Handling sensitive data takes deliberate design, so I keep full-detail working data private and only publish redacted, aggregated tables. Hashing is not always real protection: an IPv4 address hash can be reversed by brute force, and a hash of a weak password can be recovered in seconds. I also learned to state limitations up front: three days cannot show trends over time, and the honeypot settings differed between sensors, so conclusions must be careful.
